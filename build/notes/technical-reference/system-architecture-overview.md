# System Architecture Overview

**Status:** Production
**Date:** 2025-11-07
**Audience:** Developers, AI assistants working on Contextify

---

## Executive Summary

Contextify monitors AI coding conversations (Claude Code, Codex CLI) and displays them in a real-time timeline with LLM-generated summaries. This document explains the high-level architecture, component roles, and data flow.

**Key Components:**
- **StartupCoordinator**: Project identity arbiter
- **TranscriptOrchestrator**: Database API layer
- **ConversationMonitor**: Timeline UI controller
- **Follow Mode**: Session display policy

---

## Core Concepts

### Data Model Hierarchy

```
Project (Workspace)
  ├─ path: /Users/rob/code/myapp
  ├─ id: "CE962F2E-..." (stable UUID)
  └─ Transcripts (Conversation Files)
      ├─ Transcript 1: session-ABC123.jsonl (Claude Code)
      ├─ Transcript 2: session-XYZ789.jsonl (Codex CLI)
      └─ Entries (Messages in conversation)
          ├─ Entry 1: User message "Add login feature"
          ├─ Entry 2: Assistant response "I'll add authentication..."
          └─ Summaries (LLM-generated present/past forms)
              ├─ Present: "Adding login feature"
              └─ Past: "Added login feature"
```

**Key Relationships:**
- One **project** has many **transcripts** (user may have multiple AI conversations open)
- One **transcript** represents a single conversation file (JSONL format)
- One **transcript** has many **entries** (user/assistant messages)
- One **entry** may have a cached **summary** (generated by Apple Intelligence)

### Projects

- Represents a codebase/workspace (e.g., `/Users/rob/code/myapp`)
- Has stable **database ID** (UUID, never changes)
- Has **filesystem path** (metadata, can change if user moves folder)
- **Active project** = which codebase is currently being monitored

### Transcripts & Sessions

- **Transcript**: A single conversation file in JSONL format
  - Example: `~/.claude-code/history/ABC123.jsonl`
  - Append-only log of conversation events
  - One file per AI session

- **Session**: UI representation of a transcript
  - Includes: `provider` (Claude Code/Codex), `identifier`, `fileURL`, `lastActivity`, `entryCount`
  - Displayed in transcript inventory view
  - User can switch between sessions within a project

**Multiple sessions per project:** User might have:
- Session 1: "Adding authentication" (Claude Code, yesterday)
- Session 2: "Fixing bug in login" (Codex CLI, today)
- Session 3: "Refactoring database" (Claude Code, today)

### Timeline Entries

- **Entry** = one turn in the conversation
  - User message: "Add a login feature"
  - Assistant response: "I'll help you add authentication..."

- **Entry states:**
  - **Cached**: Has LLM-generated summary (e.g., "Adding authentication")
  - **Generating**: Summary being created in background
  - **Not queued**: Needs summary but not yet queued
  - **Error**: Summary generation failed

- Entries displayed in **timeline view** (chronological conversation log)

### Follow Mode

Determines **which session's entries** appear in the timeline:

**Automatic Mode (default):**
- Timeline always shows the **newest/most active session**
- When user starts new AI conversation → timeline auto-switches to it
- Like "always follow the current tab"

**Manual Mode (pinned):**
- User explicitly pins timeline to a specific session
- Timeline stays on that session even if user creates new conversations
- Used for reviewing older work or comparing sessions
- Like "lock this tab in place"

**Policy Persistence:**
- Follow mode preference saved per project in database
- When switching back to project → automatically restores follow mode
- Example: Pin to "Adding auth" session, switch projects, return → still pinned to "Adding auth"

## Component Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                        ContextifyApp                             │
│                     (SwiftUI Entry Point)                        │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ├──→ StartupCoordinator (Identity)
                             ├──→ ProjectSwitcherState (Project List)
                             └──→ ConversationMonitor (Timeline)
                                          │
                                          ├──→ TranscriptOrchestrator (Database)
                                          ├──→ TimelineCacheMissGenerator (LLM)
                                          └──→ ActiveSessionPolicyEngine (Follow Logic)
```

### StartupCoordinator (Project Identity Arbiter)

**Role:** Single source of truth for which project is active

**Responsibilities:**
- Publishes `ActiveProjectContext` (project ID + path + display name + git branch)
- Ensures project exists in database before monitoring starts
- Coordinates startup order: App → Switcher → Timeline
- Handles project switching atomically (all subsystems receive same update)

**Key API:**
```swift
// App launch
try await StartupCoordinator.shared.start()

// Wait for initial project
let context = try await StartupCoordinator.shared.ready()

// Subscribe to project changes
for await context in StartupCoordinator.shared.updates() {
    // Handle new active project
}

// User switches project
try await StartupCoordinator.shared.switchProject(to: newPath)
```

**Why it exists:**
- Prevents race conditions (multiple subsystems trying to resolve project simultaneously)
- Guarantees database is ready before monitoring starts
- Provides stable project ID (doesn't change even if folder moved/renamed)

**Detailed docs:** `startup-coordinator-architecture.md`

---

### TranscriptOrchestrator (Database API Layer)

**Role:** High-level database operations for transcripts and entries

**Responsibilities:**
- CRUD operations (projects, transcripts, entries, cache)
- Transcript ingestion (JSONL files → database rows)
- File watching (monitors transcript files for changes via FSEvents)
- Query API (get recent feed, get entries after cursor, etc.)

**Key Components:**
- `HooverEngine`: Streams JSONL files into database incrementally with crash-safe checkpointing
- `TranscriptWatcher`: File system monitoring for real-time updates
- Repositories: Type-safe database access (ProjectRepository, EntryRepository, CacheRepository, etc.)

**Thread Safety:**
- `@unchecked Sendable` - can be called from any thread
- GRDB connection pool handles concurrent access
- WAL mode enables concurrent reads while writing

**Key API:**
```swift
// Get recent timeline entries
let feed = try orchestrator.getRecentFeed(
    forProject: projectId,
    limit: 25,
    generatorSignature: "v1"
)

// Ingest new transcript
try orchestrator.upsertTranscripts(
    projectId: projectId,
    discovered: [transcript]
)

// Get/set follow policy
let policy = try await orchestrator.getFollowPolicy(projectId: projectId)
try await orchestrator.setAutomatic(projectId: projectId)
```

**Why it exists:**
- Abstracts SQL complexity from UI layer
- Provides type-safe database operations
- Handles schema migrations and data validation
- Centralizes file watching and ingestion logic

**Detailed docs:** `sql-backend-architecture.md`, `app/Sources/ContextifyCore/Database/README.md`

### ConversationMonitor (Timeline UI Controller)

**Role:** Manages what's displayed in the timeline view

**Responsibilities:**
- Loads entries from database and displays in UI
- Filters entries by active session (respects follow mode)
- Queues entries for LLM summarization (viewport-based)
- Manages follow mode (automatic vs manual session tracking)
- Coordinates background tasks:
  - Discovery (find new transcript files)
  - File watching (detect changes and re-ingest)
  - Health monitoring (ensure watchers still running)
  - Polling (fallback if FSEvents fails)

**Key State:**
- `entries: [TimelineEntry]` - All loaded entries
- `visibleEntries: [TimelineEntry]` - Filtered by active session (cached derived state)
- `followMode: FollowMode` - Automatic or Manual(pinned)
- `activeSession: TranscriptSession?` - Currently displayed session
- `isMonitoring: Bool` - Whether actively monitoring project
- `currentProjectId: String?` - Which project we're monitoring

**Isolation:** `@MainActor` (all state updates on main thread)

**Key API:**
```swift
// Start monitoring a project
ConversationMonitor.shared.startMonitoring(projectId: projectId)

// Switch to specific session
await monitor.switchToSessionFromUser(session)

// Switch to automatic mode
await monitor.switchToAutomatic()

// Get visible entries for UI
let entries = monitor.visibleEntries
```

**Why it exists:**
- Single source of truth for timeline UI state
- Coordinates complex interactions (DB queries, LLM generation, file watching)
- Provides SwiftUI-friendly `@Observable` interface
- Handles session switching logic and follow mode

**Detailed docs:** `conversation-monitor-state-architecture.md`

### TimelineCacheMissGenerator (LLM Summarization)

**Role:** Background generation of entry summaries using Apple Intelligence

**Responsibilities:**
- Maintains LIFO queue (newest entries first) with viewport-aware pruning
- Generates dual-form summaries (present: "Adding feature", past: "Added feature")
- Writes cache to database (keyed by content + window hash)
- Respects user edits (never overwrites user-edited summaries)
- Prunes invisible entries before LLM call (88% prevention rate during fast scrolling)

**Architecture:**
- Swift actor (thread-safe queue management)
- Sequential processing (one LLM request at a time, FoundationLLM limitation)
- 750ms stabilization delay (allows pruning to cancel stale work)
- No rate limits (FoundationLLM is local, no API throttling)

**Key API:**
```swift
// Queue entries for generation
await generator.queueMisses(misses)

// Check queue status
let (pending, isProcessing) = generator.getStatus()

// Subscribe to queue changes (for status bar)
for await stats in generator.observeQueue() {
    // Update UI with pending count, ETA, errors
}
```

**Why it exists:**
- Keeps UI responsive (generates summaries in background)
- Prevents duplicate work (deduplicates by content hash)
- Efficient processing (only generates for visible entries)

**Detailed docs:** `llm-processing-architecture.md`, `timeline-cache-llm-architecture.md`

### ActiveSessionPolicyEngine (Follow Mode Logic)

**Role:** Pure functional decision engine for session switching

**Responsibilities:**
- Decides which session should be active based on:
  - Current follow mode (automatic vs manual)
  - Available sessions (with entry counts and timestamps)
  - User actions (explicit switches)
  - System events (new sessions detected)
- Enforces global cooldown (prevent rapid switching)
- Returns decision with reasoning (for debugging/audit)

**Pure Function:**
```swift
func decide(inputs: Inputs) -> Decision

struct Inputs {
    let followMode: FollowMode
    let allSessions: [SessionKey]
    let currentActive: SessionKey?
    let entryCountsBySession: [SessionKey: Int]
    let timestampsBySession: [SessionKey: Date]
    let lastSwitchAt: Date?
    let now: Date
}

struct Decision {
    let nextActive: SessionKey?
    let shouldEmitEvent: Bool
    let reason: SwitchReason
}
```

**Why separate engine:**
- Testable (pure function, no side effects)
- Predictable (same inputs → same output)
- Auditable (decision includes reasoning)
- Reusable (can be tested in isolation)

**Detailed docs:** `build/notes/feature-specs/active-transcript-follow/IMPLEMENTATION_PROGRESS.md`

## Initialization Flow

### App Launch Sequence

```
1. ContextifyApp.init()
   └─→ StartupCoordinator.shared.start()
       ├─→ Resolve project root (env var > bookmark > persisted path > CWD)
       ├─→ Ensure project in database (getOrCreateProject)
       ├─→ Resolve git branch
       └─→ Publish ActiveProjectContext via AsyncStream

2. ProjectSwitcherState.start() (after coordinator)
   └─→ Subscribe to coordinator.updates()
       └─→ On each context update:
           ├─→ activeProjectId = context.id
           └─→ refreshProjects() (reload project list)

3. ContentView.task
   └─→ StartupCoordinator.shared.ready() (blocks until context available)
       └─→ ConversationMonitor.shared.startMonitoring(projectId: context.id)
           ├─→ Initialize TranscriptOrchestrator (database connection)
           ├─→ Create TimelineCacheMissGenerator (LLM summarization)
           ├─→ Start background tasks (discovery, watching, health, polling)
           ├─→ Load initial feed from database
           └─→ Setup notifications and set isMonitoring = true
```

### Project Switch Flow

```
User action (e.g., click project in switcher)
   └─→ ProjectSwitcherState.switchToProject(project)
       └─→ StartupCoordinator.shared.switchProject(to: path)
           ├─→ Ensure project in database
           ├─→ Create new ActiveProjectContext
           └─→ Publish to coordinator.updates() stream

All subscribers receive context simultaneously:
   ├─→ ProjectSwitcherState.handleContextUpdate(context)
   │   ├─→ activeProjectId = context.id
   │   └─→ refreshProjects()
   │
   ├─→ ConversationMonitor.handleContextUpdate(context)
   │   ├─→ stopMonitoring() (cancel old project tasks)
   │   ├─→ clearEntries() (remove old timeline data)
   │   └─→ startMonitoring(projectId: context.id) (start new project)
   │
   └─→ HUDViewModel (coordinator subscriber)
       └─→ Update git info (branch display)
```

## Startup Paths: Legacy vs Coordinator

### Current Architecture Issue

**Problem:** There are currently TWO initialization paths that run simultaneously, causing duplicate `loadFeedFromSQL()` calls.

#### Legacy Path (lines 355-529 in `startMonitoring()`)

When `ConversationMonitor.startMonitoring()` is called:

1. Initialize TranscriptOrchestrator
2. **Set `currentProjectId = projectId`** ← This triggers coordinator path!
3. Shutdown old generator, create new one
4. Initialize diagnostics HTTP server
5. Start background tasks
6. **Load feed from database** (FIRST CALL)
7. Setup cache notifications
8. Set `isMonitoring = true`

#### Coordinator Path (lines 623-657 in `onProjectOrSessionChange()`)

Triggered by `currentProjectId` didSet observer:

1. Cancel previous startup task
2. Load follow policy from database
3. Load all sessions
4. Reconcile policy with sessions
5. Load persisted cursor
6. **Load feed from database** (SECOND CALL - DUPLICATE!)
7. Replay switch events
8. Set `isReadyForUpdates = true`

### Why Both Exist

The coordinator path was added later (Nov 5, 2025) for follow mode/session management, but the legacy path wasn't fully refactored. Setting `currentProjectId` in the legacy path triggers the coordinator path via `didSet`, causing both to run in parallel.

### What Each Path Does

**Legacy path handles:**
- Orchestrator initialization
- Generator lifecycle (with shutdown chaining for CXT-1)
- Background tasks (discovery, watching, health monitoring)
- Diagnostics HTTP server
- Setting `isMonitoring = true`

**Coordinator path handles:**
- Session policy/follow mode restoration
- Cursor persistence (for incremental updates)
- Switch event replay (for audit trail)
- Setting `isReadyForUpdates = true`

**They are NOT redundant** - they do different things and need to be merged, not eliminated.

### Solution (TODO)

Prevent `onProjectOrSessionChange()` from running during `startMonitoring()` initialization:

**Option 1:** Guard in `onProjectOrSessionChange()` to skip if in initial setup
**Option 2:** Remove didSet trigger, manually call when needed
**Option 3:** Add deduplication flag to prevent second `loadFeedFromSQL()`

This is tracked as a known issue and will be addressed in a future refactor.

## Data Flow Diagrams

### Timeline Entry Lifecycle

```
1. User types in AI tool (Claude Code/Codex)
   └─→ AI tool appends to JSONL file (~/.claude-code/history/ABC123.jsonl)

2. TranscriptWatcher detects file change (FSEvents)
   └─→ Debounced update notification (100ms)
       └─→ ConversationMonitor.watchForDebouncedTranscriptUpdates()

3. HooverEngine ingests new entries
   └─→ Read JSONL from last checkpoint
       └─→ Parse and insert into database (transcript_entries table)

4. ConversationMonitor receives DB notification
   └─→ loadFeedFromSQL() (incremental cursor-based query)
       └─→ Check cache for summaries
           ├─→ Cache hit: Display entry with summary
           └─→ Cache miss: Display with .generating state
               └─→ TimelineCacheMissGenerator.queueMisses()

5. LLM Generation (background)
   └─→ Process one entry at a time (LIFO: newest first, viewport-aware pruning)
       └─→ FoundationLLM.summarizeTimelineWithForms()
           └─→ Generate present/past forms
               └─→ Save to cache (timeline_cache table)
                   └─→ Post notification
                       └─→ ConversationMonitor.refreshCachedEntries()
                           └─→ UI updates with summary ✅
```

### Session Switching

```
User clicks "Pin to Session" in inventory
   └─→ ConversationMonitor.switchToSessionFromUser(session)
       ├─→ PolicyEngine.decide() (returns Manual mode decision)
       ├─→ Set followMode = .manual(sessionId, provider)
       ├─→ TranscriptOrchestrator.setManual(projectId, sessionId, provider)
       │   └─→ Write to follow_policies table
       │
       ├─→ TranscriptOrchestrator.insertSystemEvent()
       │   └─→ Write switch event to system_events table
       │
       ├─→ Update activeSession = session
       └─→ visibleEntries recomputed (filtered by session)
           └─→ UI updates to show only pinned session entries ✅
```

## Common Confusion Points

### Q: What's the difference between Coordinator and Orchestrator?

**StartupCoordinator:**
- Coordinates **subsystems** (Switcher, Monitor, HUD)
- Manages **project identity** (which project is active)
- Handles **startup sequencing** (who goes first)

**TranscriptOrchestrator:**
- Orchestrates **database operations** (SQL queries)
- Manages **transcript ingestion** (JSONL → DB)
- Handles **file watching** (FSEvents monitoring)

**Think of it as:**
- Coordinator = "project traffic controller" (directs subsystems)
- Orchestrator = "database librarian" (manages data)

### Q: What's the difference between Transcript and Session?

**Transcript:**
- Database/file system concept
- Physical JSONL file on disk
- Database table: `transcripts`
- Example: `ce6e090b-603e-484a-977e-546214573964.jsonl`

**Session:**
- UI concept (how we talk about transcripts in the app)
- SwiftUI representation with display properties
- Struct: `TranscriptSession(provider, identifier, fileURL, lastActivity, entryCount)`
- What user sees in "Transcript Inventory" view

**They're the same thing, different layers:**
- Transcript = storage layer
- Session = presentation layer

### Q: Why are there two initialization paths?

See "Startup Paths: Legacy vs Coordinator" section above. Short answer: The coordinator path was added later for session management, but the legacy path wasn't refactored. They need to be merged.

### Q: When does LLM summarization happen?

**Triggered by:** Viewport visibility (entries user can see)
**Timing:** After 1.25s debounce (scrolling has settled)
**Processing:** Sequential (one at a time), LIFO priority (newest first), viewport-aware pruning
**Cache:** Keyed by content + window hash (deduplicates identical entries)

**Not triggered by:**
- Background/hidden entries (user hasn't scrolled to them yet)
- Entries user scrolled past quickly (debounce prevents wasted work)
- Entries with existing cache (cache hit)

## Glossary

- **Project**: Codebase/workspace being monitored (has stable UUID + filesystem path)
- **Transcript**: Single conversation file in JSONL format (one AI session)
- **Session**: UI representation of a transcript (displayed in inventory)
- **Entry**: One message in conversation (user or assistant turn)
- **Timeline**: Chronological view of entries from active session
- **Follow Mode**: Policy for which session to display (automatic vs manual)
- **Cache Miss**: Entry without LLM-generated summary (needs generation)
- **Viewport**: Which entries are currently visible to user (for queueing)
- **Cursor**: Bookmark for incremental database queries (avoids re-reading all data)
- **Orchestrator**: Database API layer (CRUD operations)
- **Coordinator**: Project identity arbiter (single source of truth)
- **Monitor**: Timeline UI controller (what to display)
